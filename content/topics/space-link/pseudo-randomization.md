## Why it matters

Receivers recover their timing from the changes between ones and zeros. Real telemetry can contain long runs of identical bits (idle fill, zeroed buffers), and those runs starve the receiver of timing information. Randomization breaks up such patterns. If the ground forgets to undo it, or undoes it with the wrong pattern, the link can show perfect frame lock while every block fails to decode.

:::claim{label="standard" source="CCSDS-401" loc="§2.4.9"}
CCSDS 401.0-B-32 notes that symbol clock recovery usually takes its timing from coded symbol transitions, that transitions alone do not guarantee stable lock, and that a pseudo-randomizer improves lock stability; it recommends limiting runs of identical coded symbols to 64 and setting minimum transition densities (125 per 1000 symbols for Category A, 275 per 1000 for Category B).
:::

## Plain-language explanation

Before transmission, every block is combined bit by bit (XOR) with a long, fixed pseudo-random pattern that both ends know. On the ground, applying the same pattern again restores the original data. Because the pattern is published in the standard, anyone can undo it: it hides nothing, it only makes the signal "busy" enough for the receiver.

## Precise terminology

:::claim{label="standard" source="CCSDS-131.0-B-6" loc="§10.1, §10.2.1"}
The Pseudo-Randomizer is mandatory for all CCSDS-recommended modulation and coding combinations; it exclusive-ORs each bit of the codeblock, codeword or transfer frame with a standard pseudo-random sequence.
:::

:::claim{label="standard" source="CCSDS-131.0-B-6" loc="§10.4.1, §10.4.2, §10.4.3"}
The specified sequence is 131,071 bits long, generated by h(x) = x¹⁷ + x¹⁴ + 1 and seeded with 11000111000111000 at the start of every codeblock, codeword or transfer frame. A 255-bit sequence from h(x) = x⁸ + x⁷ + x⁵ + x³ + 1, seeded with all ones, may be used instead only for backward compatibility with legacy systems; the standard warns that it can create spectral lines and may not guarantee compliance with ITU power-flux-density limits.
:::

## Where in the chain

:::claim{label="standard" source="CCSDS-131.0-B-6" loc="§10.2.2–§10.2.5"}
Where randomization is applied depends on the coding: uncoded — to the transfer frame; convolutional only — to the frame before encoding; concatenated — to the R-S codeblock after R-S encoding and before convolutional encoding; Turbo or LDPC — to the codeword after encoding. The ground reverses it at the matching point.
:::

## How it works, step by step

1. The sender builds the frame and applies any block coding.
2. It XORs the block with the pseudo-random sequence, starting from the first bit.
3. It attaches the sync marker (not randomized) and transmits.
4. The receiver finds the marker, then XORs the data that follows with the same sequence.

:::claim{label="standard" source="CCSDS-131.0-B-6" loc="§10.3.1–§10.3.4"}
The sync marker is used to synchronize the pseudo-randomizer: the sequence starts at the first bit after the marker, the marker itself is neither randomized nor derandomized, and derandomization can be done by XOR on hard bits or by inverting the corresponding soft-bit values.
:::

## What operators and engineers see

There is rarely a "randomizer" indicator. Its effect shows indirectly: with the right setting, symbol and frame lock are stable and decoding succeeds; with a mismatch, lock can look normal while decoders report uncorrectable blocks or frames fail their error check.

## Misconceptions and failure symptoms

- **"Randomization is encryption."** It is not. The sequence is fixed and published in the standard, so it provides no confidentiality, integrity or authentication. Security is a separate layer (SDLS).
- **"Randomization is optional."** In CCSDS 131.0-B-6 it is mandatory for all recommended modulation and coding combinations.
- **"Any randomizer will do."** Both ends must use the same sequence, seed and application point.
- **Symptom — frame lock fine, every block uncorrectable:** check that derandomization is enabled with the same polynomial and seed. Because the marker is not randomized, the synchronizer can lock even when derandomization is wrong.

## Worked example

:::claim{label="example" loc="fictional data"}
A fictional frame starts with a run of zero octets. XOR with any sequence leaves the sequence itself: the first transmitted bits equal the first bits of the pseudo-random sequence, so the zeros are replaced by a busy, transition-rich pattern. Applying the same XOR on the ground returns the zeros. If the ground uses a different seed, the result is the XOR of two different sequences — noise-like garbage that fails decoding even though the sync marker was found.

**Answer explanation:** XOR with the same sequence twice cancels out (a ⊕ s ⊕ s = a); with two different sequences it does not.
:::
